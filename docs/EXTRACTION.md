# 从生产链路到独立项目：提取与脱敏说明

## 1. 为什么不是直接拷贝代码

生产问数链路的代码运行在公司 ERP 仓库内，依赖公司数据库、内部框架、登录态、表管理配置和业务提示词。直接拷贝会带来三个问题：

1. **合规**：真实 schema、客户数据、内部规则和密钥不能进入个人公开仓库。
2. **可运行性**：依赖公司 DAL、配置中心、权限服务和 SQL Server，外部无法启动。
3. **可展示性**：大量业务定制代码会淹没 Agent 设计本身。

因此本项目采用 **“抽象重构 + 合成数据”**：保留生产链路中被验证过的工程问题与关键机制，用零依赖、可离线运行的代码重新实现，并把所有业务对象替换为虚构的离散制造 ERP。

> 准确表述：这是“从生产 NL2SQL 链路中提取设计并重写成的独立项目”，不是“把公司代码原样开源”。

## 2. 从生产实践继承了什么

| 生产中的问题/机制 | 本仓库对应实现 | 说明 |
|---|---|---|
| 模型编造不存在的字段/表 | `Catalog` + `get_table_schema` + guard 列校验 | 生成前必须看真实 schema，未知列直接拒绝并给相近建议 |
| 禁用表、禁用字段、敏感字段 | `SQLGuard` L3/L5 | 统一在 Catalog 标记，guard 执行前阻断 |
| `SELECT *` 导致大字段/敏感列泄露 | guard `select_star` | 聚合星号 `COUNT(*)` 放行 |
| 维度表混存多种字典，漏过滤导致串数据 | `required_filters` | 例如 `dim_lookup` 强制 `lookup_type` |
| JOIN 时凭空添加字典表的类型前置条件 | 业务口径 + 表关系 + 提示词约束 | 本项目用 required_filters 与 schema 关系表达，禁止猜测 |
| SQL Server 报“列名无效”后整条重试 | `remove_invalid_projection` | 只移除报错投影列，保留其它子句 |
| GROUP BY 非聚合算术表达式报 8120 | `wrap_group_by_expression` | 只对二元算术表达式包 `SUM()` |
| 多意图问题一次生成多条 SQL | 生产中的问题拆分启发式 | 本项目把“单问题单 SQL”作为约束，复杂问题走澄清；拆分作为 P1 路线 |
| 思考模式吃掉 token，JSON 被截断 | `OpenAICompatibleLLM` 默认 `enable_thinking=false` | 对支持的模型生效；是生产踩坑后的配置 |
| 模型说“查询成功”但没有结果 | Agent 最终状态校验 | 没有 `execute_sql` 成功证据，不允许 `status=ok` |
| 失败问题沉淀为经验库 | `ExperienceStore` | 生产思路是“失败→人工答案→同类复用”，本项目强化为 candidate/verified 闸门 |
| 只读查询与超时保护 | 只读连接 + `progress_handler` + 行数上限 | SQLite 演示；生产对应只读账号与命令超时 |

## 3. 本仓库新增/强化的部分

这些不是生产代码的翻版，而是为了让项目成为“可展示的 Agent 工程”而补齐的：

| 能力 | 位置 | 价值 |
|---|---|---|
| OpenAI 兼容 tool calling 循环 | `agent.py` / `llm.py` | 真正让模型决定工具顺序，而非固定 pipeline |
| 工具注册表与 JSON Schema | `tools/base.py` | 统一参数校验、错误回灌、可扩展 |
| 8 个工具 | `tools/schema_tools.py` / `sql_tools.py` / `experience_tools.py` | schema linking、值对齐、护栏、执行、修复、记忆 |
| BM25 schema linking | `catalog.py` / `text.py` | 中文 n-gram、同义词加权、零依赖 |
| CTE 识别 | `guard.py` | 支持递归 BOM / 齐套 SQL；修复了逗号分隔 CTE 的误判 |
| 经验准入闸门 | `memory/experience.py` | 防止模型自我强化；schema hash 失效 |
| 结果集评测 | `evaluation/evaluator.py` | EX / Valid SQL / 拒答率 / 报告 |
| 离线规则模型 | `mock_llm.py` | 无 Key 可复现、CI 可跑 |
| 合成 ERP 数据 | `demo/seed.py` / `data/` | 10 张表、12 订单、9 物料、BOM/采购/工单/发货/齐套 |
| CLI / CI / 测试 | `cli.py` / `.github` / `tests` | 67 个测试，一键评测 |
| 文档 | `docs/` | 架构、工具协议、改进路线、脱敏说明 |

## 4. 刻意排除的内容

以下内容不会出现在公开仓库：

- 公司真实表名、字段、表数量、业务规则、SQL 片段、提示词原文。
- 数据库连接串、账号密码、API Key、模型密钥、内网地址。
- 客户名称、联系人、电话、订单、物料、金额等任何生产数据。
- 公司内部框架（DAL、权限、审批流、页面宿主）与部署脚本。
- 生产日志、监控指标、工单/需求编号。
- 任何可用于推断公司系统结构的截图或文档。

仓库中的“杭州智造科技有限公司”“伺服电机”“ORD-1012”等均为虚构；电话号码为 `1380000000x` 形式的占位值。

## 5. 与生产链路的差异（避免过度宣称）

| 维度 | 生产链路 | 本仓库 |
|---|---|---|
| 数据库 | SQL Server，数百张表，多账套 | SQLite，10 张合成表 |
| 生成模型 | 多模型/多供应商，含思考模式配置 | `openai` 兼容接口 + 离线 mock |
| 权限 | 登录态、角色、表管理、字段禁用 | Catalog 标记 + guard + `Principal` 行级/列级角色（一次运行一个角色，无登录态与用户体系） |
| 领域 Skill | 订单查询等技能白名单 | 单一通用 Catalog，可扩展 |
| 经验库 | 生产问题库/人工校验流程 | 精简为 candidate/verified + CLI |
| 评测 | 生产反馈与人工抽检 | 40 条冻结单轮 + 10 条多轮会话用例 + 结果集比对 + AI Judge 辅助 |
| 并发/部署 | 多进程服务、任务调度、监控 | 单进程库 + CLI |

因此：

- **可以写**：参与生产 ERP 问数链路，负责/实践了 schema 约束、SQL 护栏、确定性修复、经验沉淀、评测等工程机制。
- **不要写**：这个仓库就是公司生产系统；或 mock 的 100% 是在线模型准确率。
- **面试建议**：先讲生产中的真实难题与约束，再说明为了公开演示做了脱敏重构；两者边界要清楚。

- [x] 无生产 schema、真实表数量、字段名、业务 SQL。
- [x] 无生产数据导出、日志、截图。

- [x] LICENSE 与作者信息明确。
- [x] README 明确标注“合成数据/非生产准确率”。

如果后续要把真实评测结果写进 README，只能使用 **脱敏后的统计数字**，并注明数据集规模、模型、时间与评测方法；不能附真实问题或 SQL。
